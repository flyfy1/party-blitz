Vote your faction's throw. Rock, paper, scissors between three giant fists on screen.

Each result moves your faction's piece along a 20-square party board with stars, rockets and traps. Furthest piece wins. That's the whole rulebook.

Supabase is doing the real work

No game server. Postgres is the referee's clerk.

Phones never talk to each other and never publish. They call RPCs over HTTP and listen to one Broadcast channel. The big screen reads aggregates every 250 ms, scores each round with pure functions, and writes the board back.

The case for your vote

Six reasons Party Blitz should win.

🎪

The demo is the room

Most hackathon demos are a screen recording. Ours needs you. Everyone with a phone is in the game within seconds, no app, no login, no name to type. If the room is loud, it worked.

🧱

Supabase is load-bearing

Postgres RPCs take every input, an advisory lock enforces the player cap, RLS hides the tables, Realtime Broadcast syncs 120 phones. Remove Supabase and there is no game, not a nicer game.

📏

Designed against real limits

We read the Realtime rate limiter source to learn the per-second limit is a 60-second rolling average and that fan-out counts per subscriber. The design uses 1/6 of the Free-tier budget and never touches Presence or Postgres Changes.

⚖️

Fair by construction

Factions are balanced atomically with a sequence. Scores are per member, so idle phones hurt, not help. Names are generated server-side. Tap counts are capped by elapsed time. Precision is judged locally so Wi-Fi can't decide a round.

🛟

Built to survive a venue

Server-time countdowns, a polling fallback for lost broadcasts, channel rebuild on screen unlock, host recovery from the database after a refresh, and a bot mode that runs the whole show if the Wi-Fi dies.

🤖

Claude Code, honestly

One design doc written before the event. One prompt. Scoring is pure, unit-tested TypeScript. The README lists every decision, every rejected alternative, and every assumption we could not verify.
